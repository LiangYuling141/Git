# 定位与命名

> 本文档定义 LyMatrix TEF 的身份、边界与成熟度口径。当 README、商业材料或对外介绍与本文冲突时，以本文为准；技术设计仍以 [technical/14-unified-architecture.md](technical/14-unified-architecture.md) 为权威。

## 1. 一句话定位

**LyMatrix TEF（Trusted Execution Framework）是一个为 AI Agent 的副作用建立确定性执行边界的可信执行框架。**

它不试图让 LLM 的输出变得确定，而是保证：模型提出的任何写操作，只有在经过契约校验、证据加载、风险定级、预览快照、一次性令牌确认和幂等执行之后，才可能产生副作用；否则被阻断、拒绝或要求人工确认。

## 2. 问题

企业把 LLM 接入业务系统时，真正的风险不是"回答不准确"，而是"错误地执行了写操作"：

- 模型可以生成看起来合理、但金额、库存或权限错误的参数；
- 提示注入可以让模型绕过业务约束；
- 多 Agent 投票对同模型高度相关，无法提供独立证据；
- 事后审计只能追责，不能阻止副作用发生。

TEF 的判断是：模型输出无法被证明确定，但**执行边界可以被设计成确定**。

## 3. 核心命题

| 常见做法 | 问题 | TEF 的做法 |
|----------|------|------------|
| 靠提示词约束模型 | 可被注入、不可验证 | 把约束下沉到确定性代码 |
| 多 Agent 投票 | 同模型高相关、成本高 | 单模型 + 独立证据校验 |
| 模型直连 CRUD / SQL | 无法约束业务语义与权限 | MCP 工具 + 业务契约 |
| 执行后审计 | 只能事后追责 | 预览、确认、执行前移 |
| 自报置信度门控 | 不可校准、可被操纵 | 确定性信号触发验证 |

## 4. 做什么 / 不做什么

**做：**

- 工具调用白名单与 Schema 校验
- 契约引擎：前置条件、不变量、权限、风险、补偿
- 预览快照、diff 与风险解释
- 一次性确认令牌
- 幂等执行、事务与补偿
- 哈希链审计与回放
- 评测基准与一致性测试

**不做：**

- 不训练或微调模型
- 不提供通用 Agent 编排、记忆或 RAG 平台
- 不承诺 LLM 输出逐字确定
- 不把某个 CRM / ERP 垂直当成框架本体
- 不在未验证的情况下宣称"工业级生产可用"

## 5. 目标用户

| 用户 | 需求 |
|------|------|
| AI 平台 / 基础设施团队 | 给 Agent 一个可控、可审计的写入边界 |
| 企业架构师 | 在现有系统前增加执行治理层 |
| Agent 开发者 | 用契约和工具替代散落的业务校验 |
| 研究者 / 评审者 | 可复现的评测与失效分析 |

参考实现的直接用户：义乌及周边中小微外贸、电商、小商品贸易企业。

## 6. 成熟度

| 级别 | 定义 | 当前状态 |
|------|------|----------|
| L0 设计 | 架构、契约、威胁模型成文 | 已完成 |
| L1 参考实现 | 一个垂直端到端跑通 | 进行中：Phase 0 闭环与 Phase 1 补偿运行时已跑通并有自动化验证（2026-11-08，279 个测试，含 27 个真实数据库集成测试）；崩溃恢复与并发压测未完成，因此尚未达到完整 L1 |
| L2 框架 Beta | 核心与垂直解耦，具备 SDK、文档与测试 | 未开始（`src/tef/` 已不依赖 CRM 字段，垂直经契约与实体适配器注入，这是 L2 的前置条件而非 L2 本身） |
| L3 工业级 | 安全评审、压测、兼容性、SLA | 未开始 |

对外表述必须注明当前级别，不得把 L0 / L1 表述为 L3。"Phase 0 闭环已跑通"与"L1 已完成"是两件事，前者不构成后者的充分条件。

## 8. 与 CRM-ERP 的关系

CRM-ERP 不再是项目的最终形态，而是框架的第一个参考实现与评测载体。选择义乌赊账订单场景，是因为它同时具备多租户、金额与信用风险、库存预占、人工确认和审计合规需求，能够覆盖框架的关键路径。

框架核心不得依赖 CRM 字段、订单模型或义乌规则；垂直能力通过契约与插件注入。

## 9. 成功标准

- 危险写入拦截率、误拒率、P95、单笔成本
- 令牌重放、跨租户、提示注入等攻击样例的拦截结果
- 同一评测样本在冻结上下文下可复现
- 新增垂直只需新增契约与工具，不修改核心
